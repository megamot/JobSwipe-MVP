Проєкт "JobSwipe"
Технічне Завдання (ТЗ)
________________________________________
1. Огляд Проєкту та Поточний Стан (Контекст)
Ціль: Створення MVP-додатку пошуку роботи з інтерфейсом "свайпів" (Tinder-подібна механіка).
Стек: Бекенд/Парсинг: Python (Flask), MongoDB (Docker/Atlas). Фронтенд: HTML/CSS/JS (без великих фреймворків).
Стан Проєкту: Робочий MVP-прототип. Налаштовано парсинг Robota.ua (за ID компаній), тегування та відображення однієї детальної сторінки.
Версіонування	Проєкт знаходиться на GitHub (основна гілка main). Подальша робота ведеться у гілках функціоналу (feature/).
База даних	MongoDB (дві колекції: vacancies – частково заповнена; companies – відсутня).
________________________________________
2. Модифікація та Розширення Бекенду (Python/MongoDB)
2.1. Зміни в Структурі Бази Даних
Необхідно ввести нову колекцію та змінити логіку збереження даних:
Колекція "companies" (НОВА) - Зберігання інформації про роботодавців.	Зберігати ВСІ поля, отримані з API GET /company/{id}, без втрат і змін.
Колекція "vacancies" (ІСНУЮЧА)	- Зберігання інформації про актуальні вакансії.	Зберігати ВСІ поля, отримані з API GET /company/{id}/vacancies, без втрат і змін (включно з total, cityId, profLevelId тощо).
Колекція "users" (НОВА)	Зберігання профілів користувачів та їхніх уподобань.	Зберігати облікові дані, обрані теги, історію свайпів (liked_vacancies, rejected_vacancies).
2.2. Оновлення Логіки Парсингу (parser.py)
1.	Парсинг Компаній (Новий Крок):
-	Перед парсингом вакансій компанії (використовуючи COMPANY_IDS) додати функцію для виклику GET /company/{id}.
-	Отримані дані зберігати у колекцію companies.
2.	Парсинг Вакансій:
-	Використовувати GET /company/{id}/vacancies для отримання списку.
-	Зберігати ВСІ поля кожної вакансії у колекцію vacancies.
3.	Тегування: Тегування має відбуватися на основі копії даних, а не на оригінальному документі, щоб уникнути зміни вихідних полів.
4.	Синхронізація: Логіка upsert=True (оновлення/вставка) має бути збережена для щоденної актуалізації.
________________________________________
3. Фронтенд та Логіка Користувача (HTML/JS/Flask)
3.1. Адаптивна Верстка (Обов'язково)
•	Адаптивність: Забезпечити коректне відображення інтерфейсу (свайп-карток та кабінету) на мобільних та десктопних пристроях (Mobile-First Design).
3.2. Логіка Реєстрації та Профілю
1.	Проста Реєстрація: Створити мінімальну форму реєстрації (username, password) та логін. Зберігати дані в колекції users.
2.	Вибір Тегів: Надати користувачу інтерфейс для вибору тегів (наприклад, #Frontend, #Marketing, #Junior — з поля tags_tech). Цей вибір зберігається у профілі користувача.
3.3. Візуалізація Карток (Свайп-інтерфейс)
Картки повинні відображатися, ґрунтуючись на даних, які релевантні поточному користувачу.
a.	Логіка Фільтрації (Критично): API-маршрут /api/vacancies повинен повертати вакансії, які мають спільні теги (з поля tags_tech) з тегами, обраними користувачем у профілі.
b.	Склад Картки: Картка повинна містити:
-	Назва Компанії (companyName)
-	Місто: (Виводити "Київ" для cityId: 1, інакше виводити значення cityId).
-	Адреса (vacancyAddress).
o-	Короткий опис: Тільки перше речення з поля shortDescription.
3.4. Зберігання Реакцій та Кабінет Користувача
a.	Логіка Свайпу (/api/swipe): При свайпі (Like/Nope) запис ID вакансії додається до відповідного списку в документі користувача (liked_vacancies або rejected_vacancies).
b.	Кабінет (Liked Vacancies): Створити новий маршрут та HTML-сторінку для "Обраних вакансій".
-	Відображати сітку карток (не свайп-інтерфейс) для всіх вакансій, ID яких є у списку liked_vacancies поточного користувача.

4. Вимоги до Git та Версіонування
a.	Робоча Гілка: Всі нові функції (реєстрація, парсинг компаній, UI-кабінет) повинні розроблятися у нових гілках (наприклад, feat/auth-user-profile, feat/company-data-sync).
b.	Коміти: Кожен коміт повинен бути змістовним, описувати одну логічну зміну та відповідати стандарту: [Feat/Fix/Chore]: Зміст зміни.
c.	Фіксація: Фіксація змін має включати оновлення файлів app.py, parser.py та відповідних HTML/JS.
